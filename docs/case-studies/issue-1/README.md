# Issue 1 case study

Code Quality built an inline analyzer to track source identities through Git history. This extraction makes that analyzer installable and gives reviewers a browser view of its evidence. It preserves the first-parent v1 report at the existing Code Quality library, CLI and HTTP boundaries. [Extraction issue](https://github.com/link-foundation/code-evolution/issues/1), [Code Quality issue](https://github.com/link-foundation/code-quality/issues/1), [original implementation](https://github.com/link-foundation/code-quality/pull/2)

## How existing approaches address the requirements

| Approach                  | What it measures or provides                                                                                                                 | Consequences for this extraction                                                                                                                                                                                                                                                                                                                                             |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Git history and diffs     | Git enumerates a commit's first parents, reads exact blob objects and can infer similar file renames from a file diff.                       | Git provides auditable changeset boundaries and exact contents. File similarity is a distinct heuristic from matching declarations and cannot supply stable function or class identities on its own. Using it for file renames would also change existing v1 results. [Git rev-list](https://git-scm.com/docs/git-rev-list), [Git diff](https://git-scm.com/docs/git-diff)   |
| CodeScene hotspots        | Public documentation combines change frequency, Code Health and other factors to prioritize where refactoring could have impact.             | A hotspot backed only by v1 file events answers where activity occurred. Ranking file paths by count keeps the result reproducible from raw events and leaves priority decisions to the reviewer. [CodeScene hotspots](https://codescene.io/docs/guides/technical/hotspots.html)                                                                                             |
| CodeScene change coupling | Public documentation distinguishes commit co-change from ticket-based associations and discusses filtering and thresholds.                   | Commit pairs can be counted from the input repository alone, with an explicit omission for large commits. Ticket and time-window grouping would change the unit of observation. A frequently changing test or configuration file may couple for good reasons. [CodeScene change coupling](https://docs.enterprise.codescene.io/latest/guides/technical/change-coupling.html) |
| RefactoringMiner          | Its public documentation describes a Java API for detecting named refactorings and displaying AST diffs, including code moved between files. | Typed refactoring detectors can provide richer explanations. They would add a separate runtime and their semantics would differ from the existing multi-language hash-and-evidence API. The extracted report uses original v1 normalization and records the source of each observed change. [RefactoringMiner documentation](https://github.com/tsantalis/RefactoringMiner)  |
| Refactoring graphs        | Brito, Hora and Valente studied 1,150 nontrivial refactoring graphs across 10 Java projects, including chains of changes spanning commits.   | Multiple commits can express one larger refactoring. V1 groups equal transitions and points back to evidence, so its occurrence count answers a narrower question. The paper's counts describe a different population from the five-commit example. [Refactoring Graphs](https://arxiv.org/abs/2003.04666)                                                                   |

Keeping the analyzer in Code Quality would minimize package overhead but tie the CLI, demo and further reuse to that repository. A file-only engine based on Git would omit the abstraction-level acceptance criteria. A full parser and identity rewrite would need a new evidence corpus and contract. The chosen plan extracts the existing read-only Git traversal and syntax projection as a package, validates it with the original tests, and uses the packed candidate to exercise the consumer cutover.

## Associative stack and Meta Language

The stack baseline is Formal AI commit `015a683197c89e8f74375b097e8dd06a57dcea8f`. The executable uses `lino-arguments` for argv and Links Notation settings. The browser uses `link-foundation/ui` through `@link-foundation/ui-dom` for action controls declared in a `.lino` document and `lino-i18n` for its English catalog. Git remains the authoritative object store. The report is an on-demand JSON projection, and the browser keeps imported JSON in memory. This read-only feature requires no transaction, persistent link-store, reasoning or calculator boundary. [Pinned associative stack guide](https://github.com/link-assistant/formal-ai/blob/015a683197c89e8f74375b097e8dd06a57dcea8f/docs/associative-tech-stack.md), [Links UI](https://github.com/link-foundation/ui)

The existing pipeline uses `command-stream`. Its exact-argv runner and streaming API were considered for Git. The extracted Git adapter retains the original combined stdout/stderr byte limit before decode, 30-second deadline, process-group cancellation and matching error behavior. The wider `command-stream` API would still need a custom adapter to enforce this policy. Public search and capture belong to the research process. The engine reads only local Git objects. [Command Stream API](https://github.com/link-foundation/command-stream)

The open PR inventory covered dependency refresh #229, CST/source-preserving translation #228, and Rust layout #218. PR #228 at `3b77cb71a42c091c89d952f24acfe652ee95a1a1` is the relevant development snapshot. Its registry and syntax projection provide a CST boundary. The projection uses UTF-8 span coordinates and has its own grammar and source-preservation contracts. The existing engine needs JavaScript source offsets and stable declaration names and hashes across thirteen modes, including an original limited CMake adapter. Some CMake expansions must explicitly refuse analysis. A wholesale adoption would need fixture evidence of equivalence for these contracts. [Meta Language PR #228](https://github.com/link-foundation/meta-language/pull/228)

The extracted analyzer copies the small Meta Language grammar-kind helper from that exact revision and uses it in structural metrics. The helper bridges Tree-sitter versions that expose symbol categories differently. The existing pinned parser runtimes and CMake projection supply the rest of the contract. The grammar fixtures check valid and invalid syntax in all thirteen modes, and the Code Quality verifier compares the complete report. [Helper at pinned revision](https://github.com/link-foundation/meta-language/blob/3b77cb71a42c091c89d952f24acfe652ee95a1a1/js/src/tree-sitter-node-kind.js), [original and adapted code inventory](data/source-files.tsv)

## Observations from the generated history

The fixture starts at `57583c74ae4ff44af9c298079fbaeece1bae59e6` and ends at `f5cbf88018970626328fd80ba03eced9047a996f`. Five snapshots give 27 events and five hotspot paths. The two busiest paths, `src/metrics.py` and `src/normalize.js`, have three file events each. Three file pairs each share two commits. All three pairs share the initial baseline, illustrating how the selected window affects a coupling count. The rename preserves the formatter file ID but the hotspot count is split between the old and new paths.

The two JavaScript default-value transformations land in commit `3cbc8894b04fb1b5405b5e3113c1f276a95fb2b3` and produce a single repeated pattern. Its two evidence entries point to distinct function identities in the same path. The aggregate complexity delta is zero under the structural counter. This fixture demonstrates evidence frequency while leaving behavioral impact and maintainability to review.

Run `node examples/evolution-report/generate.mjs` to regenerate the sample from a temporary Git repository. The automated fixtures compare the complete parsed report. The browser smoke test loads the sample, filters for classes, follows the evidence to a function, opens a local JSON file, rejects an invalid report, resets the sample and checks the layout at 390 pixels. See the [checked-in browser capture](../../screenshots/code-evolution.png).
